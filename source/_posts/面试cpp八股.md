## 1.C++相关

### 1.1 命名空间

想象一下，在一个大型公司里，如果没有任何部门划分，所有员工都在一起办公。可能会有两个甚至多个员工叫“张三”。当老板喊“张三，来一下”时，就会引起混乱，因为不知道具体要找的是哪个张三。

**命名空间**就是解决这个问题的“部门”或“文件夹”。它通过给名称（变量名、函数名、类名等）加上一个前缀，来划定一个范围，从而避免命名冲突。

**为什么需要命名空间？**

1. **避免命名冲突**：这是最主要的目的。尤其是在使用多个第三方库时，很难保证这些库没有同名的函数或类。命名空间将它们隔离开。
2. **提高代码可读性和可维护性**：将逻辑上相关的代码组织到同一个命名空间下，代码结构更清晰，就像把文件分门别类地放入不同的文件夹。
3. **封装**：命名空间可以隐藏实现细节，只暴露必要的接口，这与面向对象编程的封装思想类似。

**用法：**

```c++
// 定义一个名为 "Math" 的命名空间
namespace Math {
    const double PI = 3.14159;
    
    int add(int a, int b) {
        return a + b;
    }
    
    class Calculator {
        // ... 类实现
    };
}


#include <iostream>

int main() {
    // 方式一：使用作用域解析运算符 ::
    std::cout << Math::PI << std::endl; // 输出 3.14159
    int result = Math::add(5, 3);

    // 方式二：使用 using 声明（引入单个成员）
    using Math::PI;
    std::cout << PI << std::endl; // 现在可以直接用 PI

    // 方式三：使用 using 指令（引入整个命名空间 - 慎用！）
    using namespace Math;
    int result2 = add(10, 20); // 可以直接用 add
    // 注意：这种方式可能会引起命名冲突，破坏命名空间的设计初衷

    return 0;
}
```

### 1.2 变量

一个带标签的盒子

```
数据类型 变量名 [= 初始值];
```

**1. 作用域和生命周期：**

这两个概念决定了变量“从哪里可用”以及“何时被创建和销毁”。

*   **局部变量**：在函数或代码块 `{}` 内部定义的变量。
    *   **作用域**：从定义它的地方开始，到所在的代码块结束为止。
    *   **生命周期**：程序执行到其定义处时创建，离开其作用域时被销毁。

*   **全局变量**：在所有函数（包括 `main` 函数）之外定义的变量。
    *   **作用域**：从定义它的地方开始，到整个文件结束。其他文件想使用需要用 `extern` 关键字声明。
    *   **生命周期**：在程序开始时创建，在程序结束时销毁。
    *   **注意**：应尽量避免使用全局变量，因为它们会破坏代码的封装性，导致程序难以理解和维护。

**2. 存储期**

存储期决定了变量的生命周期，主要由**存储类别说明符**控制。

* **`static`**：静态存储期。

  *   用于**局部变量**：变量在第一次执行到定义处时初始化，之后即使离开作用域，其值也会保持，直到程序结束。下次进入作用域时，使用的是之前保持的值。

  ```cpp
  void counter() {
      static int count = 0; // 只初始化一次
      count++;
      std::cout << count << std::endl;
  }
  int main() {
      counter(); // 输出 1
      counter(); // 输出 2
      counter(); // 输出 3
      return 0;
  }
  ```

  *   用于**全局变量**：将其作用域限制在**当前文件**内（称为内部链接），其他文件无法使用 `extern` 访问。

* **`extern`**：用于**声明**一个在其他地方（通常是其他文件）**定义**的变量。它告诉编译器“这个变量存在，但请去别处找它的定义”。

  ```cpp
  // file1.cpp
  int globalVar = 42; // 定义
  
  // file2.cpp
  extern int globalVar; // 声明，告诉编译器 globalVar 在别处定义了
  void foo() {
      std::cout << globalVar; // 输出 42
  }
  ```

**3. 静态变量**

（1）当一个全局变量或函数被声明为 `static` 时，它的**链接性**从**外部链接**变为**内部链接**。

- **外部链接**：该变量/函数可以被其他源文件（通过 `extern` 声明）访问。
- **内部链接**：该变量/函数只能在**当前源文件**内被访问，对其他源文件是不可见的。这相当于给它加了一个“文件作用域”的限制。

**作用：** 避免命名冲突。你可以在不同的源文件中定义同名的 `static` 全局变量或函数，而它们之间不会相互干扰。

（2）当一个**局部变量**（在函数或代码块内定义的变量）被声明为 `static` 时，它的**生命周期**从**自动存储期**变为**静态存储期**。

- **自动存储期**：变量在代码块开始时创建，在代码块结束时销毁。每次进入代码块都会重新初始化。
- **静态存储期**：变量在程序**第一次执行到其声明处时初始化**，并在程序的整个生命周期中都存在。即使函数调用结束，变量也不会被销毁，**其值会保持**。下次调用该函数时，使用的将是之前保持的值。

（3）当一个类的成员变量被声明为 `static` 时，它就成了**静态成员变量**（或类变量）。

- 它**不属于任何一个类的对象**，而是属于这个类本身。
- 它在程序开始时初始化，在所有类的对象被创建之前就已经存在。
- 类的**所有对象共享**这一个静态成员变量副本。任何一个对象修改了它，其他所有对象看到的都是修改后的值。

**作用：** 存储所有类对象共有的数据（例如，一个计数器用来统计创建了多少个对象）。

（4）当一个类的成员函数被声明为 `static` 时，它就成了**静态成员函数**。

- 它**不属于任何一个类的对象**，因此它**没有 `this` 指针**。
- 因为它没有 `this` 指针，所以它**只能访问类的静态成员变量和其他静态成员函数**，而不能访问普通的非静态成员（变量或函数）。
- 调用静态成员函数时，**不需要通过类的对象**，可以直接通过类名来调用。

**作用：** 处理与类相关但不依赖于特定对象数据的任务。

```c++
class MyClass {
public:
    static int staticVar;
    int normalVar;

    static void staticFunction() {
        staticVar = 10; // 正确，可以访问静态成员
        // normalVar = 20; // 错误！不能访问非静态成员
        // 因为没有 this 指针，不知道 normalVar 属于哪个对象
    }

    void normalFunction() {
        staticVar = 30; // 正确，非静态函数可以访问静态成员
        normalVar = 40; // 正确，访问自己的成员
    }
};

int main() {
    MyClass::staticFunction(); // 直接通过类名调用
    // MyClass::normalFunction(); // 错误！必须通过对象调用

    MyClass obj;
    obj.staticFunction();  // 也可以通过对象调用（但不推荐）
    obj.normalFunction();  // 正确
    return 0;
}
```

### 1.3 vector 和 list 相关

**（1） vector和list在内存管理上有什么区别？底层内存分配和管理机制上，它们有什么不同？**

**回答话术：**
“`vector`和`list`在内存管理上的区别是根本性的，源于它们的底层数据结构：`vector`是动态数组，而`list`是双向链表。

1. **内存布局与分配：**
   - **`vector`**：它一次性申请一大片**连续的**内存空间。当当前空间不足时，它会**重新分配**一块更大的内存（通常是原大小的1.5或2倍），然后将所有原有元素**移动（move）或拷贝（copy）** 到新内存，并释放旧内存。这个过程叫做“重新分配（reallocation）”。
   - **`list`**：它的元素是分散在内存各处的。每次插入一个新节点（`push_back`），都是单独从堆上申请一小块内存来存放这个节点和指向前后节点的指针。**内存是非连续的，没有重新分配的过程。**
2. **管理机制：**
   - **`vector`** 的管理核心是**容量（capacity）** 和**大小（size）** 的概念。它需要预分配多余的空间以避免频繁重新分配。
   - **`list`** 的管理核心是**节点（node）** 之间的**指针链接**。每个节点都知道它的邻居是谁，管理开销在于每个节点都需要额外的指针空间和每次插入删除时的堆分配/释放操作。”

**核心区别：** `vector`是**批量分配**的**连续**空间，存在`realloc`成本；`list`是**逐个分配**的**非连续**空间，存在每个节点的额外开销。

------

**（2）那如果在多线程环境下，一个线程不停push_back，另一个线程用迭代器遍历，不加锁的话会有什么问题？vector和list表现会一样吗？**

**回答话术：**
“绝对会有问题，这会导致**未定义行为（Undefined Behavior）**，但两者的具体表现和根本原因完全不同。

- **对于vector：** 这是**极其危险**的。因为`push_back`可能导致**重新分配**。一旦发生重新分配，整个内存块地址会变。但遍历线程对此一无所知，它持有的迭代器（本质上是一个指向旧内存的指针）会立刻**失效**。继续使用这个迭代器就是在访问已被释放的内存，必然导致程序崩溃（Segmentation Fault）。**它的崩溃是剧烈且必然的。**
- **对于list：** 同样危险，但表现可能更“诡异”。`list::push_back`会在链表尾部创建一个新节点并修改原尾节点的`next`指针。如果遍历线程刚好在读取这个原尾节点的`next`指针时，`push_back`线程正在修改它，就会导致**数据竞争（Data Race）**。这可能会读到脏数据、导致遍历遗漏新节点或重复遍历，甚至因为指针错乱而访问非法地址，造成偶发性崩溃。**它的崩溃是偶发且难以复现的。**

**结论：** 两者在不加锁的多线程读写情况下都不安全，但`vector`由于迭代器极易失效，问题更直接；`list`的问题则在于指针操作的原子性无法保证。”

------

**（3） list的push_back不会替换已有节点数据那为什么还会出现访问悬空指针的情况？**

**回答话术：**
“您说得对，`push_back`不会破坏已有节点，但它会**修改现有节点的指针**。问题的根源就在于此。

假设我们有一个只有一个节点的链表：`A -> nullptr`。
线程A执行`push_back(B)`，这个过程分解为：

1. 创建新节点`B`，`B.next = nullptr`。
2. 将节点`A.next`从`nullptr`**修改为指向B**。

如果在线程A刚刚执行完步骤1但还没执行步骤2的**极短时间窗口内**，线程B正在遍历。它看到`A.next`仍然是`nullptr`，于是认为`A`是尾节点，遍历结束。这不会崩溃，只是漏掉了B。

但更危险的情况是，如果线程A在修改`A.next`的**中间状态**（因为指针赋值不是原子的，在某些架构上可能需要多条指令）被线程B读到了，线程B可能会读到一个**破损的、非法的指针值**。用这个值去访问内存，立刻就会导致悬空指针访问和崩溃。”

------

**（4） 你想清楚这个链表结构的next指针在什么时候可能有问题？**

**回答话术：**
“`next`指针在以下几个时刻会出问题：

1. **写入期间（写撕裂）：** 如上一题所述，在指针被写入完成前，其他线程可能读到一个中间状态的值。
2. **读取期间：** 当一个线程正在读取`node->next`时，另一个线程可能已经`delete`了这个`next`指向的节点。这样，当前线程读到的指针虽然值没问题，但它指向的内存已经被释放，变成了悬空指针。
3. **删除操作期间：** 这是最复杂的。如果线程A正在删除节点`X`（`A->X->B`要变成`A->B`），它需要先让`A.next = B`，然后再`delete X`。如果在`A.next`已经指向`B`但`X`还未被`delete`的瞬间，线程B正在遍历，它可能顺利通过。但如果`delete X`已经执行，线程B才走到`X`，并通过`X.next`去访问，就会访问已释放的内存。

所以，即使只是遍历，只要和写操作并发，就存在读到正在被修改的指针或已释放节点的风险。”

### 1.4 套接字通信相关

**（1）TCP套接字阻塞模式和非阻塞模式下send()的行为有啥区别？**

**回答话术：**
“最核心的区别是：**当内核的发送缓冲区（Send Buffer）没有足够空间时，两者的行为截然不同。**

- **阻塞模式：** `send()`函数会**一直挂起（阻塞）** 当前线程，直到内核缓冲区有足够的空间容纳要发送的数据，或者发生错误（如连接断开）才会返回。
- **非阻塞模式：** `send()`函数会**立即返回**。如果缓冲区有空间，它返回实际写入的字节数。如果缓冲区已满，它不会等待，而是立刻返回一个错误码（如`EAGAIN`或`EWOULDBLOCK`），意思是“本来想阻塞，但因为是非阻塞模式，所以告诉你现在发不了”。”

**简单说：阻塞模式会等，非阻塞模式不等，直接告诉你结果。**

------

**（2）如果内核缓冲区没满呢？是什么样的情况，如果满了呢？**

**回答话术：**

- **缓冲区没满：** 这是最理想的情况。无论阻塞还是非阻塞模式，`send()`都会**立即**将数据从用户缓冲区拷贝到内核的发送缓冲区，然后返回实际拷贝的字节数。**注意：`send()`返回并不代表数据已经发送到对端，只代表数据已成功交给操作系统内核。**
- **缓冲区满了：**
  - **阻塞模式：** 调用线程被投入睡眠，直到内核网络栈将缓冲区中的数据发送出去一部分，腾出足够空间后，才会唤醒线程完成`send()`操作。
  - **非阻塞模式：** `send()`立即返回`-1`，并设置`errno`为`EAGAIN/EWOULDBLOCK`，告知应用程序“请稍后再试”。

------

**（3）那非阻塞模式下你是怎么判断什么时候可以重试发送的？**

**回答话术：**
“粗暴的做法是忙等待（busy-loop），但这会浪费CPU。高效的做法是使用**I/O多路复用（I/O Multiplexing）** 机制，比如 **`epoll`**（Linux）或 `kqueue`（BSD）。

具体流程是：

1. 当`send()`返回`EAGAIN`时，我不再直接重试。
2. 我将这个socket注册到`epoll`实例中，并监听其**可写（EPOLLOUT）** 事件。
3. 然后我的线程可以去处理其他已经就绪的socket（比如处理可读事件）。
4. 当内核的发送缓冲区有空间了，`epoll`就会通知我：“这个socket现在可以写了”。
5. 此时，我再调用`send()`进行重试，这时成功率就非常高了。

这种方式让单个线程可以高效地管理成千上万个非阻塞socket，只在socket真正可读写时才进行操作，避免了无谓的循环和CPU浪费。”

------

**（4）要自己写个定时器轮询吗有没有更高效的做法？**

**回答话术：**
“不需要自己写定时器轮询。正如我刚才提到的，**使用`epoll`这样的I/O多路复用机制就是最高效的做法**。它是由操作系统内核提供的，能够在内核态直接监控大量文件描述符的状态变化，然后以事件的形式通知给应用程序，而不是让应用程序去轮询每个socket，这极大地提高了效率。

自己写定时器轮询是效率最低下的方案，应该避免。”

------

**（5） 阻塞模式下send()卡住了它什么时候才会返回？内核缓冲区是怎么工作的？缓冲区没满时会怎样？**

**回答话术：**
“阻塞模式下`send()`卡住后，会在以下情况下返回：

1. **成功：** 内核缓冲区腾出了足够空间，数据被拷贝进去，返回拷贝的字节数。
2. **错误：** 连接被对端关闭或出现网络错误，返回`-1`并设置相应的`errno`（如`EPIPE`）。
3. **信号中断：** 操作被系统信号（signal）中断，返回`-1`且`errno`为`EINTR`。

**内核缓冲区的工作方式**：它是一个**队列（FIFO）**。应用进程调用`send()`将数据拷入队列尾部，操作系统内核的网络协议栈（TCP/IP）从队列头部取出数据，组装成TCP报文段发送出去。发送成功后，这部分数据才会从队列头部移除。

**缓冲区没满时**：工作流程非常顺畅，数据直接从用户态拷到内核缓冲区，`send()`调用立即返回。”

------

**（6） shared_ptr有什么缺点或者容易出错的地方？**

**回答话术：**
“`shared_ptr`虽然好用，但有几个明显的缺点：

1. **性能开销：** 它的引用计数是原子操作，虽然线程安全，但比非原子操作开销大。拷贝和析构时都需要修改计数，有额外的性能损耗。
2. **内存开销：** 每个`shared_ptr`控制块除了引用计数，还可能包含弱引用计数、自定义删除器等，需要占用额外内存。
3. **循环引用：** 这是最经典的陷阱。如果两个对象互相用`shared_ptr`指向对方，它们的引用计数永远无法降为0，导致内存泄漏。必须用`weak_ptr`来打破循环。
4. **不透明性：** 代码中大量使用`shared_ptr`会让所有权关系变得模糊，难以清晰知道到底是哪个`shared_ptr`最后持有对象。”

**（7）事件驱动模型和一连接一线程**

- **一连接一线程（Thread-per-Connection）**：是一种**同步阻塞模型**。它为每一个到来的连接都分配一个独立的线程，该线程负责处理这个连接上的所有I/O操作，在操作完成前，线程会被阻塞。比较适合cpu密集。
- **事件驱动（Event-Driven）**：是一种**异步非阻塞模型**。它使用一个或少量线程，通过一个**事件循环（Event Loop）** 来监听所有连接上的事件（如“数据可读”、“连接可写”），当事件发生时才进行相应的处理。”比较适合I/O密集型场景。

> Reactor多线程模型
>
> - **主线程（Reactor 线程）**：仅负责处理 **I/O 事件**，不碰业务逻辑。具体工作包括：监听并接受新连接、监听已连接的读写事件（如客户端发来了数据）。
> - **业务线程池**：主线程触发 I/O 事件后，不自己执行业务逻辑，而是将 “业务处理任务”（如解析数据、计算、操作数据库）**分发到线程池中的空闲线程**，由这些线程并行处理业务。
> - **结果回调**：业务线程处理完后，将结果返回给主线程，再由主线程将响应发送给客户端（避免业务线程直接操作网络 I/O，保证 I/O 处理的统一性）。

在Linux平台，我们谈论事件驱动模型，**几乎等价于在谈论基于`epoll`的Reactor模式**。

### 1.5 C++11新特性

#### **（1）完美转发**

完美转发是 C++11 引入的一个重要特性，它允许函数模板将其参数**无损地**（保持其值类别：左值、右值、const、volatile 等）转发给其他函数。这是实现通用包装函数、工厂函数等的关键技术。

完美转发依赖于两个 C++11 特性：

1. **右值引用** (`T&&`)

   - `T&&`是**万能引用（Universal Reference）**，能接收左值、右值、const 左值等所有类型的参数，并推导出正确的`T`类型。

2. **引用折叠规则** (Reference Collapsing Rules)

   当引用的引用出现时，会按照以下规则进行折叠：

   **只要有一个是左值引用（`&`），最终结果就是左值引用；只有当两个都是右值引用（`&&`）时，结果才是右值引用**

   - `T& &` → `T&`
   - `T& &&` → `T&`
   - `T&& &` → `T&`
   - `T&& &&` → `T&&`

3. **std::forward** 函数模板

   `std::forward` 是一个条件转换，只有当参数原本是右值引用时，才会将其转换为右值。

```c++
#include <iostream>
#include <utility> // 包含std::forward

// 模板函数：通过万能引用T&&接收参数，并转发给其他函数
template <typename T>
void forward_func(T&& arg) {
    // 利用引用折叠和std::forward保持arg的原始属性（左值/右值）
    target_func(std::forward<T>(arg)); 
}

void target_func(int& x) {
    std::cout << "接收左值引用: " << x << std::endl;
}

void target_func(int&& x) {
    std::cout << "接收右值引用: " << x << std::endl;
}

int main() {
    int a = 10;
    forward_func(a);       // 传入左值，转发后仍为左值 → 调用target_func(int&)
    forward_func(20);      // 传入右值，转发后仍为右值 → 调用target_func(int&&)
    return 0;
}
```

**为什么要完美转发**

1. **编写通用库代码**：当你不知道用户会传递左值还是右值时
2. **实现工厂函数**：需要将参数原样传递给构造函数时
3. **创建包装器或装饰器**：需要将调用转发给底层实现时
4. **处理回调或事件**：需要保持参数值类别时
5. **性能优化**：希望避免不必要的拷贝操作时
6. **编写可变参数模板**：需要处理任意数量和类型的参数时

#### **（2）自动类型推导（auto）**

让编译器根据初始化表达式自动推导变量类型，简化代码书写。

#### **（3）右值引用和移动语义**

解决不必要的深拷贝问题，极大提升性能。

- **右值引用 (`T&&`)**: 绑定到临时对象（右值）的引用。
- **移动语义**: 将资源（如动态内存）从一个对象“窃取”到另一个对象，避免昂贵的拷贝。
- **`std::move`**: 将左值强制转换为右值引用，表示“我不再需要这个对象了”。

```c++
class MyString {
private:
    char* m_data;
public:
    // 移动构造函数
    MyString(MyString&& other) noexcept // 参数是右值引用
        : m_data(other.m_data) {        // 窃取资源
        other.m_data = nullptr;          // 将原对象置为空，防止其析构时释放资源
        std::cout << "Move Constructor called" << std::endl;
    }

    // 移动赋值运算符
    MyString& operator=(MyString&& other) noexcept {
        if (this != &other) {
            delete[] m_data;        // 释放自己的旧资源
            m_data = other.m_data;  // 窃取新资源
            other.m_data = nullptr;
        }
        std::cout << "Move Assignment called" << std::endl;
        return *this;
    }
    // ... 其他成员函数
};

int main() {
    MyString s1("Hello");
    MyString s2 = std::move(s1); // 调用移动构造函数，s1 被“掏空”
    MyString s3("World");
    s3 = std::move(s2);          // 调用移动赋值运算符，s2 被“掏空”
    return 0;
}
```

2. `std::shared_ptr`

共享所有权的智能指针，使用引用计数。可以被多次拷贝。

- 引用计数本质是 “共享该内存的 `shared_ptr` 数量”。

```c++

        std::cout << *ptr2 << std::endl;
    } // ptr2 析构，引用计数-1
} // ptr1 析构，引用计数为0，内存释放
```

当你创建一个`std::shared_ptr`时（例如`std::shared_ptr<int> sp(new int(42));`），系统会做两件事：

1. 在堆上分配对象本身（这里是`int(42)`）；
2. 同时分配一个控制块（Control Block），这个控制块包含：
   - 强引用计数（`strong count`）：记录当前有多少个`shared_ptr`持有该对象（决定对象何时销毁）；
   - 弱引用计数（`weak count`）：记录当前有多少个`weak_ptr`“观察” 该对象（决定控制块何时销毁）；
   - 其他信息（如对象的删除器`deleter`等）。

1. 按值捕获

   **语法**：通过`[var]`或`[=]`声明（`var`是具体变量名，`=`表示捕获所有外部变量）。
   **行为**：lambda 会创建外部变量的**副本**并存储在内部，后续对该变量的访问 / 修改仅针对这个副本，**不影响外部原始变量**。按值捕获不能修改变量

2. 引用捕获

   **语法**：通过`[&var]`或`[&]`声明（`&var`表示只捕获 var 的引用，`&`表示捕获所有外部变量的引用）。
   **行为**：lambda 内部存储的是外部变量的**引用**，对变量的访问 / 修改会**直接影响外部原始变量**。

#### （7）浅拷贝、深拷贝、移动语义和完美转发

**浅拷贝 (Shallow Copy)**

- **是什么**：只复制对象的**成员变量的值**（即按位拷贝）。如果成员变量是指针，则复制的是**指针本身**（内存地址），而不是指针所指向的数据。简单的说，两个对象会**共享同一块动态资源**（比如指针指向同一个内存地址）。
- **后果**：两个对象的指针成员指向**同一块内存**。这会导致：
  1. **dangling pointer**：一个对象析构后释放了内存，另一个对象的指针就成了悬空指针。
  2. **双重释放**：两个对象析构时都会尝试释放同一块内存，导致程序崩溃。
- **何时发生**：默认的拷贝构造函数和拷贝赋值运算符就是浅拷贝。

```cpp
class MyString {
private:
    char* data; // 动态资源（指针）
public:
    // 构造函数：分配动态内存
    MyString(const char* str) {
        data = new char[strlen(str) + 1];
        strcpy(data, str);
    }
    // 未显式定义拷贝构造，使用编译器默认的浅拷贝
    ~MyString() { delete[] data; } // 析构时释放动态内存
};

int main() {
    MyString s1("hello");
    MyString s2 = s1; // 浅拷贝：s2.data 和 s1.data 指向同一块内存
    // 程序结束时：s2先析构，释放data指向的内存；s1再析构时，会释放已被释放的内存→崩溃！
    return 0;
}
```

**深拷贝 (Deep Copy)**

- **是什么**：不仅复制成员变量的值，还为指针成员**重新分配新的内存**，并将原指针指向的内容**完整地复制一份**到新内存中。
- **后果**：两个对象完全独立，拥有各自的资源，互不影响。
- **如何实现**：需要自定义**拷贝构造函数**和**拷贝赋值运算符**。

```cpp
class MyString {
private:
    char* data;
public:
    MyString(const char* str) {
        data = new char[strlen(str) + 1];
        strcpy(data, str);
    }
    // 显式实现深拷贝构造函数
    MyString(const MyString& other) {
        // 1. 为新对象分配独立的动态内存
        data = new char[strlen(other.data) + 1];
        // 2. 复制源资源的内容到新内存
        strcpy(data, other.data);
    }
    ~MyString() { delete[] data; }
};

int main() {
    MyString s1("hello");
    MyString s2 = s1; // 深拷贝：s2.data 指向新分配的内存，内容与s1.data相同
    // 析构时：s1和s2各自释放自己的内存，无风险
    return 0;
}
```

**移动语义**

移动语义解决了深拷贝有时带来的**不必要的性能开销**。

- **是什么**：一种将资源（如动态内存、文件句柄等）从一个对象**“转移”**到另一个对象，而不进行深拷贝的机制。
- **为什么**：对于临时对象或即将销毁的对象，深拷贝其资源是一种浪费。直接“偷”走它的资源更高效。
- **如何实现**：通过定义**移动构造函数**和**移动赋值运算符**来实现。它们接受一个**右值引用 (`&&`)** 参数。

**完美转发**

完美转发解决了在**模板函数**中如何保持参数的**原始值类别**（左值/右值）并将其无损地传递给另一个函数的问题。

- **问题场景**：在编写通用包装函数或工厂函数时，你希望将接收到的参数原封不动地传给另一个函数。

> **演进关系**：
>
> 1. **浅拷贝有问题** -> 引入**深拷贝**来解决正确性问题。
> 2. **深拷贝有性能开销** -> 引入**移动语义**来优化临时对象的处理。
> 3. 为了在通用代码中**更好地利用移动语义** -> 引入**完美转发**来无损地传递参数。
>
> 在面试中，你可以这样串联起来回答：
> “**浅拷贝和深拷贝**是解决对象复制的基本方法，深拷贝保证了正确性但可能有性能成本。**移动语义**则是对深拷贝的一个重要优化，它通过转移资源所有权来避免不必要的拷贝，特别适用于临时对象。而为了在编写模板函数时能充分利用移动语义，我们需要**完美转发**机制来保持参数的原始值类别，从而选择最合适的构造函数或函数重载。”
>
> - **移动语义**：聚焦于 “对象资源的高效转移”，通过区分左值（可长期存在）和右值（临时 / 即将销毁），允许函数 “窃取” 右值的资源（如动态内存、文件句柄），减少拷贝开销。
> - **完美转发**：聚焦于 “参数值类别的精准传递”，确保在模板函数转发参数时，原始参数的左值 / 右值属性不丢失，从而让被调用函数（如移动构造函数、接受右值的函数）能正确选择重载版本。

#### **（8）总结**

1. **让代码更简洁易读**：`auto`, 范围 `for`, Lambda。
2. **提升运行时性能**：右值引用/移动语义, `constexpr`。
3. **提升安全性**：智能指针, `enum class`, `nullptr`。
4. **拥抱现代多核硬件**：标准线程库。
5. **增强泛型编程能力**：可变参数模板, 完美转发。

### 1.6 函数模板

函数模板是一个**蓝图或公式**，用于生成针对特定类型的函数。它允许我们编写一次代码，然后用于多种数据类型，而不需要为每种类型都重写函数。

```c++
// 定义一个函数模板
template <typename T>  // 或者 template <class T>
T max(T a, T b) {
    return (a > b) ? a : b;
}

int main() {
    int a = 5, b = 10;
    std::cout << max<int>(a, b) << std::endl; // 输出 10
    
    double x = 3.14, y = 2.71;
    std::cout << max<double>(x, y) << std::endl; // 输出 3.14
    
    return 0;
}
```

函数模板本身不是函数，而是**生成函数的蓝图或公式**。编译器使用这个蓝图在需要时生成具体的函数代码。

这个模板不会直接编译成机器码，而是告诉编译器："当你看到有人使用`max`函数时，根据实际类型生成对应的函数"。

### 1.7 设计模式

设计模式是软件设计中常见问题的可重用解决方案。它们不是可以直接转换为代码的完整设计，而是解决特定问题的模板或描述。

1. **创建型模式**：处理对象创建机制（单例、工厂、建造者等）
2. **结构型模式**：处理对象组合（适配器、装饰器、代理等）
3. **行为型模式**：处理对象间的通信和责任分配（观察者、策略、命令等）

#### （1）单例模式

单例模式确保一个类只有一个实例，并提供一个全局访问点。

懒汉式：

```c++
class Singleton {
private:
    Singleton() {} // 私有构造函数
    
    // 禁用拷贝和赋值
    Singleton(const Singleton&) = delete;
    Singleton& operator=(const Singleton&) = delete;

public:
    // 获取单例实例（C++11保证局部静态变量初始化是线程安全的）
    static Singleton& getInstance() {
        static Singleton instance;
        // 当第一次调用 getInstance() 时，instance 被初始化。
        // 后续所有调用都直接返回这个已初始化好的实例。
        // 在程序结束时，实例会自动销毁。
        return instance;
    }
    
    void doSomething() {
        // 业务逻辑
    }
};


int main() {
    // 1. 获取单例实例（第一次调用时创建对象）
    Singleton& instance1 = Singleton::getInstance();
    
    // 2. 使用实例：调用成员函数
    instance1.setConfig("production");
    std::cout << "配置: " << instance1.getConfig() << std::endl; // 输出：production

    instance1.increment();
    instance1.increment();
    std::cout << "计数: " << instance1.getCount() << std::endl; // 输出：2

    // 3. 再次获取实例（与instance1是同一个对象）
    Singleton& instance2 = Singleton::getInstance();
    std::cout << "instance2 计数: " << instance2.getCount() << std::endl; // 输出：2（与instance1共享状态）

    // 4. 尝试拷贝或赋值（编译报错，因为已被delete）
    // Singleton copy = instance1; // 编译错误
    // instance2 = instance1;      // 编译错误

    return 0;
}

// 饿汉式
class EagerSingleton {
private:
    static EagerSingleton instance;  // 静态对象，类加载时初始化

    EagerSingleton() {}  // 私有构造
    EagerSingleton(const EagerSingleton&) = delete;
    EagerSingleton& operator=(const EagerSingleton&) = delete;

public:
    static EagerSingleton& getInstance() {
        return instance;  // 直接返回已初始化的实例
    }
};

// 类外初始化静态对象（程序启动时执行，调用构造函数）
EagerSingleton EagerSingleton::instance;
```

- **饿汉式**是在程序启动、类加载的时候就直接创建实例。它的优点是实现简单，并且天生就是线程安全的。缺点是如果这个实例最终没有被使用，会造成资源的浪费，也可能会拖慢程序的启动速度。
- **懒汉式**是只有在第一次调用 `getInstance()` 方法时才会去创建实例。它的优点是资源利用率高，只有在需要的时候才创建。缺点是实现上需要考虑线程安全问题，通常需要用双检锁等机制来保证，不过在现代C++中，使用局部静态变量可以很简洁地实现线程安全的懒汉式。

### 1.9 内存对齐

内存对齐是指数据在内存中的存储起始地址必须是某个特定值的整数倍，这个值通常是2的幂次方（1、2、4、8、16等）。比如一个4字节的int类型变量，通常需要存储在4的倍数地址上。

"举个例子，考虑这样一个结构体：

```c++
struct Example {
    char a;      // 1字节
    int b;       // 4字节  
    short c;     // 2字节
};
```

如果不考虑对齐，大小应该是7字节，但实际上在64位系统上通常是12字节。这是因为："

1. "char a占用1字节（偏移0）"
2. "需要3字节填充，使int b从偏移4开始（4的倍数）"
3. "int b占用4字节（偏移4-7）"
4. "short c占用2字节（偏移8-9）"
5. "最后需要2字节填充，使整个结构体大小为4的倍数"

  操作系统层面

     │  └─ BSS段：存储未初始化的全局/静态变量（默认零初始化）

  ```

### 1.12 stream流

C++ 的 “流（stream）” 是**统一处理输入输出的抽象机制**，它将数据传输抽象为 “流动” 的过程，通过 `cin`、`cout`、文件流等对象，提供了与设备无关、类型安全且易于扩展的 I/O 操作方式。无论是控制台、文件还是字符串，都可以通过相同的流操作语法处理，是 C++ 中 I/O 编程的核心。

流的高效性依赖于**缓冲区（Buffer）**：数据不会直接写入 / 读取设备，而是先存入内存中的缓冲区，当缓冲区满、手动刷新（如 `endl`）或关闭流时，**才会一次性写入 / 读取设备**。这减少了对硬件的直接操作次数，提升了性能。

例如 `cout << "Hello"` 会先将字符串存入缓冲区，而 `cout << "Hello" << endl` 中的 `endl` 会同时完成 “换行” 和 “刷新缓冲区” 的操作。

### 1.13 类型转换

**（1）旧式转换**

**语法：** `(type)expression` 或 `type(expression)`

**示例：**

```cpp
int i = 10;
double d = (double)i;   // C风格转换
double d2 = double(i);  // 函数式风格转换
```

**缺点：**

1.  **过于强大**：它会尝试任何可能的转换，包括不安全的转换。
2.  **难以搜索**：在代码中很难通过搜索找到所有使用旧式转换的地方。
3.  **缺乏安全性**：编译器不会帮你检查转换是否合理，容易引入难以发现的 bug。

**正因为这些缺点，在 C++ 中应尽量避免使用旧式转换，而是使用下面更安全的新式转换。**

**（2）新式转换**

1. **`static_cast` - 静态转换**

**用途**：这是最常用、最通用的转换，用于在**相关类型**之间进行“良性”和“低风险”的转换。

**典型场景：**

- **基本数据类型之间的转换**（如 `int` -> `double`, `float` -> `int`）
- **void 指针** 和 **具体类型指针** 之间的转换（`void*` -> `int*`）
- **类层次结构中的向上转换**（派生类指针/引用 -> 基类指针/引用，**安全**）
- **编译器隐式执行的任何类型转换**，你都可以用 `static_cast` 显式完成。

**示例：**

```cpp
int i = 42;
double d = static_cast<double>(i); // int -> double

void* pv = &i;
int* pi = static_cast<int*>(pv);   // void* -> int*

class Base {};
class Derived : public Base {};
Derived der;
Base* pb = static_cast<Base*>(&der); // 向上转换，安全
```

**注意**：它**不**提供运行时类型检查。用于向下转换（基类 -> 派生类）时，如果类型不对，会产生未定义行为。

---

2. **`dynamic_cast` - 动态转换**

**用途**：专门用于处理**含虚函数的类继承层次**中的**向下转换**（基类指针/引用 -> 派生类指针/引用）。它会在**运行时**进行类型检查，这是它最大的特点。

**工作机制**：它需要依赖 RTTI (Run-Time Type Information) 来确认类型的正确性。

- **如果转换成功**：返回目标类型的指针或引用。
- **如果转换失败**：
  - 对**指针**类型进行转换时，返回 `nullptr`。
  - 对**引用**类型进行转换时，抛出 `std::bad_cast` 异常。

**示例：**

```cpp
class Base { virtual void dummy() {} }; // 必须有虚函数
class Derived : public Base { /* ... */ };

Base* pb = new Derived; // 实际上指向一个Derived对象

// 向下转换，使用dynamic_cast是安全的
Derived* pd = dynamic_cast<Derived*>(pb);
// 现在pd 是一个 Derived* 类型的指针
if (pd != nullptr) { // 必须检查是否成功！
    // 转换成功，安全使用pd
    std::cout << "Conversion successful.\n";
} else {
    std::cout << "Conversion failed.\n";
}

Base* pb2 = new Base; // 指向一个纯粹的Base对象
Derived* pd2 = dynamic_cast<Derived*>(pb2);
// pd2 现在是 nullptr，因为 pb2 并不指向一个 Derived 对象

// 对于引用
try {
    Derived& rd = dynamic_cast<Derived&>(*pb); // *pb是Derived对象 → 转换成功
    Derived& rd2 = dynamic_cast<Derived&>(*pb2); // *pb2是Base对象 → 转换失败
} catch (const std::bad_cast& e) {
    std::cerr << "Bad cast: " << e.what() << '\n';
}
```

**性能开销**：因为有运行时检查，`dynamic_cast` 比 `static_cast` 慢。

---

3. **`const_cast` - 常量转换**

**用途**：这是唯一一个可以**移除或添加 `const` 和 `volatile`** 属性的转换运算符。

**典型场景：**

- **移除 const 属性**：调用一个参数不是 `const` 但实际不会修改对象的旧式函数。
- **添加 const 属性**：较少见，通常可以隐式完成。

**非常重要**：`const_cast` 并不意味着你可以修改一个原本就是常量的对象。试图修改一个原本为 `const` 的对象是**未定义行为**。

**示例：**

```cpp
void print(char* str) { // 一个旧的、不接收const指针的函数
    std::cout << str;
}

const char* message = "Hello World";

// print(message); // 错误：不能将const char*传递给char*
print(const_cast<char*>(message)); // 正确：移除了const

// --- 危险示例 ---
const int ci = 10;
int* modifiable = const_cast<int*>(&ci);
*modifiable = 20; // 未定义行为！因为ci本身是const
std::cout << ci << " " << *modifiable; // 可能输出 "10 20"，非常反直觉
```

---

4. **`reinterpret_cast` - 重新解释转换**

**用途**：这是**最危险**的转换。它提供低层次的、基于比特位的重新解释。它可以将任何指针类型转换为任何其他指针类型，甚至可以将指针转换为足够大的整数类型，反之亦然。

**典型场景：**

- **函数指针类型之间**的转换（极度危险且不可移植）。
- **指针和整数之间**的转换（例如在底层系统编程中）。
- **不相关类型的指针之间**的转换（如 `MyClass*` -> `int*`）。

**示例：**

```cpp
int i = 42;
// 将int的地址重新解释为double指针（这没有意义且危险！）
double* dp = reinterpret_cast<double*>(&i);

// 将指针转换为整数（例如存储地址值）
uintptr_t address = reinterpret_cast<uintptr_t>(&i);

// 将整数转换回指针
int* ip = reinterpret_cast<int*>(address);
```

**警告**：`reinterpret_cast` 的行为高度依赖于编译器平台。它通常用于底层、与硬件打交道的代码中。在应用程序级别的代码中，**除非你非常清楚自己在做什么，否则绝对不要使用它**。

---

**（3）对比**

| 转换类型               | 转换目标                | 检查时机   | 安全性       | 常见用途                      |
| :--------------------- | :---------------------- | :--------- | :----------- | :---------------------------- |
| **`static_cast`**      | 相关类型                | 编译时     | 中等         | 数值转换，void*转换，向上转换 |
| **`dynamic_cast`**     | 多态类型（向下转换）    | **运行时** | **高**       | 安全的向下转换，检查类型      |
| **`const_cast`**       | `const`/`volatile` 属性 | 编译时     | 低（若误用） | 移除或添加 const 属性         |
| **`reinterpret_cast`** | 任何类型                | 编译时     | **极低**     | 低层比特位重解释，危险操作    |
| **C-Style Cast**       | 任何类型                | 编译时     | **极低**     | **应避免使用**                |

> 当被问到如何选择时，可以这样回答：
>
> 1.  **首选 `static_cast`**：用于大多数明确定义且编译器认可的转换，如数值转换和向上转换。
> 2.  **需要安全的向下转换时，使用 `dynamic_cast`**：尤其是在你不确定指针所指对象的真实类型时。务必检查返回值（指针）或捕获异常（引用）。
> 3.  **需要处理 const 问题时，使用 `const_cast`**：但必须极度小心，确保你不会修改一个原本就是常量的对象。
> 4.  **尽量避免使用 `reinterpret_cast`**：除非你在进行极其底层的编程，并且完全理解其后果。它在应用程序代码中几乎是永远不需要的。
> 5.  **彻底避免使用 C 风格转换**：因为它混合了 `static_cast`, `const_cast`, 和 `reinterpret_cast` 的行为，非常危险，且意图不清晰。
>
> **核心思想**：使用新式转换可以让代码的**意图更加清晰**，编译器也能借此提供更好的**类型安全检查**，从而减少错误。

### 1.14 指针和引用

一个返回类型为引用的函数，应该返回变量本身

一个返回类型为指针的函数，应该返回&变量

```c++
#include <iostream>
using namespace std;

int main() {
    int a = 10;  // 原变量：a（值10，地址假设为0x1234）

    // 1. 引用的使用
    int& ref = a;  // 必须初始化：ref是a的别名，绑定a
    ref = 20;      // 操作引用=操作原变量：a的值变成20
    cout << "a = " << a << endl;        // 输出a=20
    cout << "&ref = " << &ref << endl;  // 取引用地址=原变量地址：0x1234


    // 2. 指针的使用
    int* p = &a;   // 初始化：p存储a的地址（0x1234）
    *p = 30;       // 必须解引用：通过地址修改a的值，a变成30
    cout << "a = " << a << endl;        // 输出a=30
    cout << "p = " << p << endl;        // 指针存储的地址：0x1234
    cout << "&p = " << &p << endl;      // 指针自身的地址：假设为0x5678（独立内存）


    // 3. 指向修改的区别
    int b = 40;
    // ref = b;  // 错误理解：这不是改引用的指向！而是把b的值赋给ref（即a），a变成40
    p = &b;       // 正确：指针可以改指向，现在p存储b的地址（假设0x9abc）
    *p = 50;      // 修改b的值：b变成50
    cout << "b = " << b << endl;        // 输出b=50
    cout << "a = " << a << endl;        // a还是30（指针改指向不影响原变量）

    return 0;
}
```

### 2.1 linux了解吗？文件系统知道哪些，Linux有哪些锁？

Linux 支持多种文件系统。最主流的是 **ext4**，它稳定可靠，是很多发行版的默认选择。**XFS** 在高性能和大文件处理上更有优势，常用于服务器。面向未来的有 **Btrfs**，它提供了快照、压缩等高级功能。对于 SSD，有专门优化的 **F2FS**。此外，还有像 **procfs** 和 **sysfs** 这样的虚拟文件系统，用于暴露内核信息。”

**锁机制：**
“Linux 的锁分为几个层次。在**多线程编程**中，最常用的是 **pthread 互斥锁 (Mutex)** 来保证互斥访问。**读写锁**适用于读多写少的场景以提高并发性。**自旋锁**则用于临界区非常短且不想承受线程切换开销的情况。对于**多进程同步**，特别是操作同一个文件时，可以使用 `flock` 或 `fcntl` 设置的**文件锁**。”

**如何选择锁？**

- 保护**多线程**的共享数据 -> **互斥锁 (pthread_mutex_t)**
- 保护**多进程**的共享资源（如共享内存）-> **进程间互斥锁 (pthread_mutex_t with PTHREAD_PROCESS_SHARED)** 或 **信号量 (Semaphore)**
- 保护**很短**的临界区（且是多核CPU）-> **自旋锁 (pthread_spinlock_t)**
- 保护对**同一个文件**的访问 -> **文件锁 (flock/fcntl)**

## 3.多线程

### 1.线程数的选择

**1. CPU 密集型任务：线程数 ≈ CPU 核心数**

**CPU 密集型任务**指任务主要消耗 CPU 资源（如数据计算、逻辑处理、加密解密等），线程几乎一直在使用 CPU，很少等待 IO（磁盘 / 网络）。

- **为什么？**：若线程数超过 CPU 核心数，多余的线程会因争夺不到 CPU 而进入就绪态，等待调度。此时，频繁的线程上下文切换（保存 / 恢复线程状态）会消耗大量 CPU 资源，反而降低整体效率。

**2. IO 密集型任务：线程数 ≫ CPU 核心数**

**IO 密集型任务**指任务大部分时间在等待 IO 操作（如数据库查询、网络请求、文件读写等），CPU 利用率低。

- **为什么？**：线程在等待 IO 时会被挂起（不占用 CPU），此时可创建更多线程处理其他任务，充分利用 IO 等待的 “空闲时间”。

### 2.线程池的参数

- **核心线程数（corePoolSize）**：线程池长期维持的最小线程数，即使空闲也不会销毁（除非设置允许核心线程超时）。
- **最大线程数（maximumPoolSize）**：线程池能创建的最大线程数，超过后会触发拒绝策略。
- **阻塞队列（workQueue）**：核心线程满时，临时存放任务的队列（如 LinkedBlockingQueue、ArrayBlockingQueue）。
- **拒绝策略（RejectedExecutionHandler）**：队列和最大线程数都满时，处理新任务的方式（如丢弃任务、抛出异常）。
- **空闲线程存活时间（keepAliveTime）**：非核心线程空闲超过该时间后，会被销毁以节省资源。

>以 “用户提交一个任务” 为起点，线程池的处理流程可细化为 7 个关键步骤，结合 “工厂车间” 类比更易理解（核心线程 = 固定工人，非核心线程 = 临时工，队列 = 物料仓库）：
>
>1. **任务提交**：用户通过`execute()`或`submit()`提交任务，线程管理器先判断线程池是否处于`RUNNING`状态（非`RUNNING`则直接触发拒绝策略）。
>2. **核心线程判断**：检查核心线程是否有空闲 / 未创建满（核心线程数 < corePoolSize）：
>
>  - 是：直接创建新的核心线程，执行当前任务（相当于 “工厂招固定工人，来了活直接干”）。
>  - 否：进入下一步。
>
>3. **队列判断**：检查阻塞队列是否还有空位（任务数 < 队列容量）：
>
>  - 是：将任务存入队列，等待核心线程空闲后从队列中取任务执行（相当于 “固定工人都在忙，物料先存仓库，等工人有空再处理”）。
>  - 否：进入下一步。
>
>4. **非核心线程判断**：检查当前总线程数是否未达到maximumPoolSize（总线程数 < maximumPoolSize）：
>
>  - 是：创建非核心线程执行任务（相当于 “仓库满了，临时雇几个临时工帮忙，避免物料堆积”）。
>  - 否：进入下一步。
>
>5. **触发拒绝策略**：此时 “核心线程满 + 队列满 + 非核心线程满”，按预设的拒绝策略处理新任务（相当于 “工厂满负荷，新订单接不了，按规则告知客户”）。
>6. **线程复用逻辑**：无论是核心线程还是非核心线程，执行完当前任务后，不会立即销毁，而是循环从阻塞队列中获取新任务（take()或poll()方法）：
>
>  - 核心线程：若队列有任务则继续执行，无任务则保持空闲（除非允许核心线程超时）。
>  - 非核心线程：若队列有任务则继续执行，无任务且空闲时间超过`keepAliveTime`，则被线程管理器销毁（“临时工没事做，到点下班”）。
>
>7. **线程池状态切换**：若调用`shutdown()`，线程池进入`SHUTDOWN`状态：不再接受新任务，但会执行完队列中已有的任务；若调用`shutdownNow()`，则进入`STOP`状态：立即中断所有正在执行的线程，且丢弃队列中的任务，最终进入`TERMINATED`状态（线程池完全关闭）。

### 3.c++中多线程相关

**（1）c++11中如何创建线程**

- 创建：通过`std::thread t(func, args...)`，传入函数 / 函数对象 /lambda 表达式。

- 操作：`join()`（阻塞等待线程结束，回收资源，可以理解为 “**主线程停下来，等子线程做完再继续**”。）、`detach()`（线程后台运行，脱离主线程控制，需确保线程访问的资源生命周期，`detach()` 后，子线程仍在后台运行，但它访问的资源（如主线程的局部变量、堆内存）必须保证在子线程结束前有效，**否则会导致 “悬垂引用” 或 “野指针”**。）、`get_id()`（获取线程 ID）。

  | 维度             | `join()`                                                     | `detach()`                                                 |
  | ---------------- | ------------------------------------------------------------ | ---------------------------------------------------------- |
  | **阻塞性**       | 会阻塞调用它的线程（如主线程），直到子线程执行完毕。         | 不会阻塞，调用后主线程可立即继续执行后续逻辑。             |
  | **资源回收**     | 子线程结束后，由 `join()` 主动回收资源（避免 “僵尸线程”）。  | 子线程结束后，系统自动回收资源，无需手动干预。             |
  | **线程对象状态** | 调用后，线程对象不再关联任何实际线程（成为 “空线程”）。      | 调用后，线程对象不再关联任何实际线程（成为 “空线程”）。    |
  | **调用限制**     | 只能调用一次，多次调用会导致未定义行为（程序可能崩溃）。     | 只能调用一次，多次调用会导致未定义行为。                   |
  | **子线程依赖**   | 适合子线程的结果被主线程依赖的场景（主线程需要子线程的计算结果）。 | 适合子线程独立运行、不依赖主线程且主线程无需其结果的场景。 |

- 注意：线程对象销毁前必须调用`join()`或`detach()`，否则会调用`std::terminate()`终止程序。

**（2）线程的生命周期与转换**

- 状态：新建（`std::thread`创建未启动）、就绪（线程可被调度）、运行（CPU 执行中）、阻塞（等待资源 / 条件，如`wait()`、IO）、终止（函数执行完毕）。
- 转换：`join()`会让主线程阻塞到子线程终止；`wait()`会让线程从运行→阻塞；`notify()`会让阻塞→就绪。

**（3）互斥锁之间的区别**

- `std::mutex`：基础互斥锁，提供`lock()`/`unlock()`，需手动配对（易漏解锁导致死锁）。

- `std::lock_guard`：RAII 封装，构造时`lock()`，析构时`unlock()`，适合简单场景（锁范围固定）。
- `std::unique_lock`：更灵活，支持`lock()`/`unlock()`手动控制，可配合条件变量（`condition_variable`要求传入`unique_lock`），但性能略低于`lock_guard`。

**（4）读写锁**

- 作用：读多写少场景下提高并发效率（读操作可共享，写操作独占）。
- 读操作：用`std::shared_lock<std::shared_mutex>`（共享锁，多个线程可同时持有）；
- 写操作：用`std::unique_lock<std::shared_mutex>`（独占锁，仅一个线程持有）。

**（5）atomic？与互斥锁的区别？是否绝对线程安全？**

- 作用：提供原子化操作（如`++`、`load`、`store`）（load、store用于在多线程环境中**原子地读取和写入变量的值**），底层通过 CPU 指令（如`lock cmpxchg`）保证操作不可分割，无需加锁。
- 区别：原子操作轻量（无上下文切换），适合简单操作（计数器、标志位）；互斥锁适合复杂逻辑（多步操作需原子性）。
- 单个原子操作是线程安全的，但复合操作（如`a += b`后再`c = a`）不一定安全，需额外同步。

**（5）`std::future`、`std::promise`、`std::async`的作用？**

- 用于线程间传递结果（异步操作）：
  - `std::promise`：生产者线程设置结果（`set_value`）；
  - `std::future`：消费者线程获取结果（`get()`，阻塞直到结果就绪）；
  - `std::async`：异步启动任务，返回`future`（参数`launch::async`立即创建线程，`launch::deferred`延迟到`get()`时执行）。

**（6）`thread_local`的作用？使用场景？**

- 线程局部存储：每个线程拥有独立的变量实例，生命周期与线程一致。
- 场景：线程私有状态（如日志 ID、临时缓存）、替代`static`避免线程安全问题（如`errno`在多线程中是`thread_local`的）。
